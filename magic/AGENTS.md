# Magic 项目规则

> 这里只放"每次干活都该被提醒的规矩"。状态与知识在 `magic/docs/` 里，别往这里加。
> fork 根那份 `AGENTS.md` 是上游给 harness 贡献者的，不作为我们的规则；本文件才是。

## 1. 方向（错不得的一条）

产品 = **DSH fork 底座 + 我们直接改的官方外壳 + `magic/` 产品层**。

- 唯一产品工作目录是 `D:\Harmess\dsh-0.1.6`，分支 `magic/main`。
- 不再自建客户端、不再抄底座输出、不再往产品仓里搬第三方 vendored 源码。
- 底座已经做到的能力是"读源码"的对象，不是"复制一份归我们管"的对象。
- **不追上游更新**：已经裁定不再使用上游后续版本内容，所以不存在"保持可 rebase"的约束；
  代价是我们改了哪些文件只能靠登记表回忆 —— 所以每一处改动都必须登记（见 §5）。

## 2. 回答技术问题前：先看源码，别迎合

1. 回答任何关于 Magic 或底座的技术问题前，必须先查相关真实源码；禁止凭通用经验、记忆、
   PRD、README、目录名或"官方应该是这样"来推断实现。
2. 说"项目现在就是这样做的""某功能如何实现"时，必须给仓库名、源码路径、具体行号。
3. 未查到源码、或源码不足以证明，就明说"未核实"或"待技术核查"；不把推测包装成结论。
4. 需要对照官方实现时：先读底座源码，再读 `magic/` 下的我们的代码，最后给结论。
5. 用户的方向有问题要直接指出并纠正，不能只服从；但**不替用户做决定** —— 涉及产品语义、
   有副作用或不可逆的动作，先问。
6. **路线决策给一个答案**（可以／不可以／建议 X）+ 代价，不给用户摊菜单。
7. 体验基准唯一性：界面行为、交互与视觉的唯一基准是**我们自己的 Magic 实例实际渲染出来的样子**
   （`node magic/scripts/start-web.mjs` 起来那台）。官方裸壳形态不是基准；被我们改过、被插件
   接管或注入过的任何形态，一律以本机实测为准。
8. 验收要说"跑过什么、看到什么"，不说"应该能用了"。加载成功 ≠ 功能可用。

## 3. 产品语义

产品语义（工作方式、任务账本、责任、审批、副作用治理）的唯一真源是 `magic/docs/产品/` 下的 PRD。
语义变更先改对应 PRD 再改代码；不新建平行 PRD。新能力的取舍按
`magic/docs/对标-3099基线.md` 的判据：**需求来自 3099，实现优先来自底座**。

## 4. 代码放哪儿

| 要放的东西 | 放哪儿 |
| --- | --- |
| 我们的插件 | `magic/plugins/<名>/`，包名 `@magic/<dsh-名>` |
| 挂载清单 | `magic/patches/`（权威片 `magic.patch.yml`；过渡片清空即删） |
| 启动与开发脚本 | `magic/scripts/` |
| 文档（产品定义、边界、裁定、对标） | `magic/docs/` |
| 底座能力 | **不复制**，读 `packages/*/*` 源码 |
| 第三方 vendored 插件 | 留在原地，按路径引用；**不搬进产品仓、不提交** |

## 5. 改动纪律

1. 用户只问问题时，只核实并回答；只有用户明确要求时才改代码或文档。
2. 改动前说明文件、依据、目的和影响范围；只做完成任务所需的最小改动。
3. **改 `magic/` 以外任何文件，源码里留 `Magic fork delta:` 注释，并在
   `magic/docs/底座边界.md` 登记表加一行**（文件、改了什么、为什么、怎么回退）。
4. **不得改槽位契约**：槽名、owner props、cardinality 一变，挂在 `ctx.slots` 上的全部插件
   一起崩。要换某个官方部件的表现，用 `ctx.slots.register` 复用同一 cell + priority 影子。
5. **界面改造按四层递进，能停上层就不进下层**：① `ui-theme` 令牌表 → ② skeleton 布局 →
   ③ 槽位影子替换单个部件 → ④ 改官方组件源码。第 ④ 层每动一处都要进 §5.3 的登记表。
6. 新能力优先做成插件；只有属于"我们的界面与产品形态"的东西才改进底座；不复制底座的
   session / tool / agent-loop / llm。
7. 挂产品插件不改 `apps/desktop` 源码 —— 走包内 `dsh.bundle.patch` 的 in-repo bundle 路线。
8. **废弃内容用归档而不是删除**：转向先改规则与 PRD、写清状态，再动代码；打上 tag 并留取回命令。
   **归档过的东西，其缺陷清单同时作废**，不要当成待办搬进新路线。
9. 批量前先做单点试点（搬 N 个包之前先端到端跑通最小的一个，并给比测试更强的等价证据）。
10. 多步任务之前先要一页执行计划，不靠逐步"继续吗"往前滚。

## 6. 构建与运行（细节见 `docs/底座边界.md`）

```
node magic/scripts/start-web.mjs --no-open --port 3097     # 起 Magic 实例
pnpm run build:lib:host                                    # 出 lib/index.js（Node 半）
pnpm run build:lib:client                                  # 出 lib/client.js（浏览器件）
pnpm run build:web                                         # 出前端壳 apps/web/dist
```

- 带 `dsh.client` 的包**两半分属两个 pass**，只跑一面会漏另一半。
- 改任何底座包要跑该包 `pnpm run bundle` 才生效；`apps/web` 的 `vite build` 全绿对客户端包是空跑。
- `lib/`、`*.tsbuildinfo` 不入库；`git add` 目录前先确认没把构建产物扫进去。
