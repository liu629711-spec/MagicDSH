# 仓库与文档收口方案

> 这份东西本身是新结构里的第一个文件。签了字才开始动别的文件。

## 0. 方向（一段话，错不得）

产品 = **DSH fork 底座 + 我们直接改的官方外壳 + `magic/` 产品层**。

- 唯一工作目录：`D:\Harmess\dsh-0.1.6`，分支 `magic/main`，远端 `origin` = MagicDSH。
- 不再自建客户端、不再从别的仓跨目录引用代码。
- `D:\Harmess\Magic` 收口后转**只读历史**：产品定义搬进来，代码与文档的旧份随 tag 归档。
- 底座已经做到的能力（session / tool / agent-loop / llm / 权限 / 47 个客户端包 / Electron 壳）
  是"读源码"的对象，不是"抄一份归我们管"的对象。

## 1. 目标目录结构

```
MagicDSH/                       ← 唯一工作目录（分支 magic/main）
├─ packages/ apps/ vendor/ native/ benchmarks/ website/
│                             ↑ 上游区。能不改就不改；改了必须登记（见 §1.2）
├─ magic/                     ← 产品区，全部是我们的东西
│  ├─ plugins/                我们的 8 个插件 + 对表后决定留下的 vendored 第三方
│  ├─ patches/                挂载清单。**只有一片**：magic.patch.yml
│  ├─ scripts/                启动与开发脚本（含从老仓搬来的 start-web.mjs）
│  ├─ docs/                   产品文档五件（见 §2），本文件在此
│  └─ archive/                收口期的一次性物证（能力对表原稿等），只进不出
└─ AGENTS.md                  ← fork 根，规则与现状（见 §3）
```

### 1.1 三条硬边界

1. **我们的代码只在 `magic/` 下。** 包名保留 `@magic/*` scope。
2. **改上游任何文件，必须留 `Magic fork delta:` 注释**，并在 `magic/docs/底座边界.md`
   登记一条（文件、位置、为什么、回退方法）。目前已存在 4 处：root `tsdown.config.ts`、
   `tsconfig.host.json`、`tsconfig.client.json`、`packages/client/tsdown.client.ts`、
   `scripts/client-build-environment.ts`。登记表是唯一能让我们日后看清"我们把壳动了多少"的地方。
3. **界面改造按四层递进，能停上层就不进下层**：① `ui-theme` 令牌表 → ② skeleton 布局 →
   ③ 槽位影子替换单个部件 → ④ 改官方组件源码。第 ④ 层每动一处都要进登记表。

## 2. 文档收成五件

**判据一句话：底座已有的能力不写文档，去读源码和上游 docs；我们只写"底座给不了的"（产品语义）和"我们的决定"（边界与裁定）。**

| 文件 | 装什么 | 从哪来 |
| --- | --- | --- |
| `magic/docs/README.md` | 一页索引：产品是什么、现在做到哪、每类问题去哪份文件 | 新写 |
| `magic/docs/产品/`（PRD 若干） | 产品语义唯一真源：CEO 工作方式、任务账本、责任与审批、副作用治理 | **重写**（不复制老 PRD 来改）：老 4 份的"实现与交付形态"章节是按已废弃的自建壳写的，搬进来只会污染新结构；先定 PRD-01 的本版要点，再逐份覆盖语义 |
| `magic/docs/底座边界.md` | fork delta 登记表 + 槽位契约禁改清单 + 构建怎么跑（host/client 两半分属两个 pass 这类坑） | 新写，内容来自 AGENTS.md 与今天的实测 |
| `magic/docs/决策记录.md` | 追加式：日期 + 裁了什么 + 为什么 + 推翻了什么 | 把散在 patch 注释、AGENTS、文档里的裁定收拢成一份时间线 |
| `magic/docs/对标-3099基线.md` | 3099 每条能力 × 底座有无官方对应（给源码路径）× 结论（用官方/留自研/退场/新建） | 老 `02-实现/10` 的**能力列**重做；缺陷列作废 |

老 `docs/02-实现/` 11 份的默认归宿是**归档**：其中 00、09、10 描述的是已废的自建路线；其余每份在归档前
只做一个动作——判断"在新底座上还成立吗"，成立的那部分并进上面五件，不成立的在 `决策记录.md`
留一行结论。原文不删，随老仓 tag 可查。

## 3. AGENTS.md 大改（方向不能错，所以规则要跟着换）

新的 `AGENTS.md` 放 fork 根，五节，**只放"每次都该被提醒的规矩"，不放状态与知识**（状态进
`底座边界.md`，裁定进 `决策记录.md`）：

1. **第一原则**（先查源码再答；给路径行号；不迎合、不确定就说未核实；体验基准=我们实例实测；
   路线问题给一个答案+代价；只在有副作用的动作上要许可）—— **基本保留**。
2. **产品定义**（一句话核心 + 分层 + 谁是真源）—— 新写，取代现在的"当前架构"。
3. **改动纪律** —— 重写，见下面的去留判定。
4. **构建与运行**（在产品目录里怎么跑起来、改哪层要跑哪条命令）—— 新写。
5. **禁改清单**（槽位契约、`magic/` 之外无我们的代码、不跟上游更新）—— 新写。

**要废掉的旧规则**（都属于已经不存在的路线）：

- "执行底座不可改"（已废除，但要换成有牙的版本：**不追上游**，改上游必须登记）
- 任何指向 `reference-project/deepseek-harness`（rc.2）作为运行底座的表述
- 3099 作为"运行基准"的措辞 → 改成"能力参考基线"；运行基准是 fork 实例
- 术语表里的「3099 运行态 `.magic-dsh-live/`」等历史坐标（移进 `决策记录.md`）
- "归档而非删除"保留，但补一句：**归档过的东西，其缺陷清单同时作废**，不要当待办搬进新路线
